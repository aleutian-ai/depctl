# BATCH-001: Decide an approach for the whole-batch sync timeout

**Epic:** Bulk Sync Batch Timeout
**Status:** done — C+D built and tested; A/B deliberately deferred, not blocking
**Depends on:** none
**Estimated size:** small (C) + small-medium (D), each self-contained

## Post-implementation note

**C** (`internal/cli/sync.go`, `RunSync`'s worker loop): each worker checks `ctx.Err()` before popping its next action; the first to see the shared batch context already `Done()` writes one aggregate "sync time budget exceeded after N of M actions completed; re-run to continue with the remaining M-N" message via `sync.Once`, and every worker exits cleanly instead of popping and independently failing. Regression test `TestRunSyncExhaustedBudgetStopsCleanlyInsteadOfCascading` (`internal/cli/sync_batch_timeout_test.go`) — verified rigorously: reverted the fix, confirmed the test reproduces the real bug shape (a per-action `FAIL ... context deadline exceeded` line, no aggregate message), restored it.

**D** (`internal/daemon/progress.go`, `internal/daemon/api/api.go`, `internal/mcp/tools.go`, `internal/cli/{query_client,status}.go`): `SyncProgress` now records each completed `SYNC_VERSION` action's real elapsed time (`Begin`/`Finish` already existed; `Begin` now also stores a start time) and the full set of planned-but-unfinished dependency names (`SetPlanned`, called once from `RunSync` alongside `SetTotal`). `Snapshot()` derives median/p90 (never a naive mean — real timing data is skewed enough that a mean would be routinely wrong) plus a confidence-labeled estimate (`"low"` below 10 samples, `"medium"`/`"high"` above it depending on observed skew) once at least one sample exists. Surfaced through `api.SyncProgress` (`Observed`/`Estimate`/`Pending`, all `omitempty`, fully additive — no breaking change), the `sync_progress` MCP tool's `SyncProgressOut` and its note text, and `daemon status`'s per-project sync line (median/p90/estimate shown; the full `Pending` name list deliberately left out of the human terminal view as noise, but present in the structured API/MCP response). No new dependency-scoping API — confirmed the CLI's existing `--dependency` (repeatable) and the MCP `sync_project(dependency: "...")` single-target call already let an agent or human act on a long `Pending` list.

Six new deterministic tests (`internal/daemon/progress_batch001_test.go`): median resists an outlier that would skew a mean; confidence is `"low"` below the sample floor and `"high"` for a large, tightly-clustered sample; `Pending` drops a name on finish regardless of success/failure; a genuine no-op run reports no Observed/Estimate data (no divide-by-zero, no misleading zero); an action that never called `Begin` (a non-`SYNC_VERSION` kind) contributes to `Done` but never to the timing sample count.

Verified: full suite green (`go build`/`vet`/`test`), `-race` clean on every touched package (`internal/cli`, `internal/daemon`, `internal/daemon/api`, `internal/daemon/client`, `internal/mcp`).

## Goal
Pick and scope a real fix for the gap [STRESS-005](../../planned/49-full-loop-stress-testing/STRESS-005-full-cold-sync-real-scale.md) found: an untargeted `ragctl sync` against a large real project (560+ never-synced dependencies) cannot complete in one invocation, because `internal/daemon/scheduler.go`'s `execute` wraps the *entire* pending plan in one `maxActionDuration = 30 * time.Minute` context, not per-dependency. Once exhausted, every remaining action in the batch fails instantly with a generic `context deadline exceeded`, indistinguishable in the output from hundreds of unrelated real per-dependency failures.

## Relevant existing behavior
`maxActionDuration`'s own code comment is explicit about why it exists: `context.WithoutCancel(s.base)` deliberately lets an in-flight sync survive `Shutdown` rather than leave a half-built generation, but that guarantee needs *some* ceiling or a single hung network call (an unreachable embedder or vector backend) keeps the scheduler goroutine — and the whole daemon process — alive forever. This is a real liveness/hang-protection guarantee, not an incidental bug, and untested at this batch scale rather than wrong by design. `longRunningRequestTimeout = 35 * time.Minute` (`internal/daemon/client/client.go`) is the client-side mirror of the same constraint on the HTTP round-trip.

## Options

**Option A — Raise the ceiling (make it larger and/or configurable).**
Bump `maxActionDuration`/`longRunningRequestTimeout` to something large enough for realistic worst-case batches (e.g. a few hours), possibly config-driven. Lowest-risk, smallest change. Doesn't actually fix the underlying shape — a large enough project (or a slow enough network) still eventually exceeds any fixed ceiling, and the failure mode (a wall of misleading per-dependency `context deadline exceeded` lines) is unchanged when it does.

**Option B — Replace the whole-batch ceiling with a per-action timeout + no-progress watchdog.**
Keep the existing per-operation timeouts (git clone's `defaultCloneTimeout`, Ollama's per-request timeout) as the real bound on any *individual* action, and let the batch loop itself run as long as it keeps making forward progress — a watchdog that resets on every completed action and only fires (aborting the batch, `Shutdown`-safe) after N minutes of *no* action completing, not after a fixed total elapsed time. This is the option that actually lets a real large-scale full sync complete in one invocation while preserving the original hang-protection guarantee (a genuinely stuck daemon still gets caught, just measured by "nothing progressed" rather than "too much wall-clock passed"). Larger, more architecturally sensitive change — touches the daemon's own liveness contract, needs real test coverage for both the happy path (a slow-but-progressing large batch completes) and the protection path (a genuinely hung call still gets killed).

**Option C — Keep the ceiling, but fail the batch cleanly instead of cascading.**
When the shared context is found already `Done()` before starting the next action, stop immediately and report one clear message ("sync time budget exceeded after N of M actions completed; re-run `ragctl sync` to continue with the remaining M-N") instead of letting every subsequent action independently fail with the same generic error. Cheap, no architectural risk, ships regardless of what A/B decide — but doesn't remove the need to manually re-invoke `ragctl sync` repeatedly to make progress on a truly large project, since each re-run only gets its own fresh 30-minute slice.

**Option D — Give the calling agent scope-planning information, instead of ragctl deciding a batching strategy for it.**
Complements C rather than competing with it: C makes the *stop* honest; D makes the decision *before or after* the stop an informed one, made by whoever's driving the sync (an MCP agent, or a human) — not baked into ragctl's own policy. ragctl keeps owning *execution* policy (concurrency, worker scheduling, GC coordination — none of that becomes agent-tunable); D only ever hands the agent information to decide *scope*: what to wait for, what to request specifically, what to accept as partial. Plugs into the existing live-progress mechanism (`daemon.SyncProgress`/`api.SyncProgress`, already polled by the `sync_progress` MCP tool and `daemon status`) rather than inventing a new channel:

- **No naive average-based ETA.** STRESS-005/STRESS-006's own timing data is heavily skewed (p90 roughly 4x the median — a handful of large dependencies dominate total runtime), so `average × remaining` would routinely be confidently wrong. Track median and p90 per-completed-action duration instead (`SyncProgress` needs `Begin`/`Finish` to record start/elapsed, not just counts), and only report an estimate once a real sample size exists — **not** the first 3-4 completions; something on the order of 10+ samples, still an arbitrary cutoff but far less misleading than a handful. Below that threshold, `sync_progress` reports observed timing data with no derived estimate rather than a confident-looking wrong number.
- **Report a confidence label alongside any estimate** (`low`/`medium`/`high`, driven by sample count and how wide the observed median/p90 spread is), so an agent reading it can weight the number appropriately rather than treating it as precise.
- `SyncProgress` also tracks the full set of planned-but-not-yet-finished dependency names (`Total` already exists as a count; this adds the actual name list, populated once at `SetTotal`-time from the flattened action queue) — not just what's currently `InFlight`.
- `api.SyncProgress` gains an `Observed` block (`Samples`, `MedianDependencySeconds`, `P90DependencySeconds`), an `Estimate` block (`RemainingSeconds`, `Confidence`), and `Pending []string` (dependency names not yet done/failed) — all additive, `omitempty`, no breaking change to the existing shape.
- **No new batching/scoping API is needed.** Confirmed by reading the actual code: the CLI's `RunSync`/`ragctl sync` already accepts a `dependencies []string` scope (repeatable `--dependency`), and the MCP `sync_project` tool already accepts a single `Dependency` to target one specific package (`internal/mcp/tools.go`'s `SyncProjectIn`). An agent that sees a long `Pending` list can already act on it today — request one specific dependency it actually needs via `sync_project(dependency: "...")`, repeated as needed, or a human can use `--dependency` for a batch — so D is purely better progress metadata surfaced through the existing mechanism, not a new scheduler feature.
- No change to `maxActionDuration`/the timeout/liveness contract at all — purely an information addition on top of whatever A/B/C ships.

## Recommendation
**C and D should ship together, now** — both are small, self-contained, no architectural risk, and directly address the two real problems found (a misleading failure wall, and no way to make an informed call about a large batch before or after hitting it). **B remains the real fix for the capacity problem itself** but changes the daemon's liveness/hang-protection contract, which is a bigger, more sensitive decision than STRESS-001's resolver-only fix — deliberately deferred, not decided here. **A is the fallback** if B's watchdog design turns out more complex than it's worth for how often real projects actually hit this (most registered projects are nowhere near terraform's scale).

## Non-goals (for whichever option is picked)
- No change to any individual operation's own timeout (git clone, Ollama's HTTP client) — those stay as they are regardless of which option ships.
- No new configuration surface beyond what the chosen option strictly needs (C/D need none; if A is later picked, one new config value; if B, no new config at all — the watchdog interval can be a constant like the timeouts it replaces).
- D reports information — it never itself decides to abort, batch, or resume a sync, and it never exposes or accepts any *execution*-policy knob (worker count, priority, concurrency, cancelling another in-flight job). Scope is the agent's call; mechanics stay ragctl's, matching the MCP tools' existing design (`prioritize_file`/`explain_call_site` give an agent context and let it choose, they don't choose for it).
- No new dependency-set/batching API on `sync_project` — the existing single-`Dependency` MCP parameter plus the CLI's existing multi-`--dependency` flag already cover "request a specific subset," confirmed against the real code before deciding this (see above), not assumed.
- D's estimate is a simple observed-timing projection (median/p90 of completed actions so far), not a per-dependency-size predictor (no attempt to estimate a specific not-yet-started dependency's likely duration from its repo size, chunk count, etc.) — good enough to inform a scope decision, not a scheduling optimizer.

## Tests
- C: a fake plan + a pre-cancelled context produces exactly one clear "budget exceeded" message, not N cascading ones.
- D: `SyncProgress`'s median/p90 computation is correct given a fixed, deliberately skewed sequence of fake action durations (proving it isn't just a naive mean); `Confidence` is `"low"` below the sample-count threshold and never reports a numeric estimate at all below some minimum floor; `Pending` correctly drops a name the moment its action finishes (success or failure) and never includes an action kind other than `SYNC_VERSION`; `Snapshot()` while `Total == 0` (a no-op run) reports no observed/estimate data rather than a divide-by-zero or a misleading `0s`.
- (If B is picked later) a fake slow-but-progressing action sequence completes past the old ceiling, and a fake truly-hung action still gets killed by the watchdog.
- STRESS-005 itself remains the live-scale confirmation, not something to re-run for every future change here.

## Acceptance criteria
- [x] C: an untargeted sync that exhausts the batch budget stops immediately with one clear message, not N cascading `context deadline exceeded` failures.
- [x] D: `sync_progress` (both the MCP tool and `daemon status`) reports median/p90 observed-duration figures, an estimated-seconds-remaining figure with an explicit confidence label (never a bare misleading number from too few samples), and the full list of not-yet-finished dependency names, once a real sample size exists.
- [ ] Re-running STRESS-005 against real `hashicorp/terraform` after C+D ship shows: either the full batch completes, or it fails with one clear "budget exceeded, re-run to continue" message (C) alongside accurate observed timing, an appropriately-confidence-labeled estimate, and the real pending-dependency list having been visible via `sync_progress` throughout the run (D) — not hundreds of misleading per-dependency `context deadline exceeded` lines. **Not yet done** — needs a real large-scale re-run (a similar cost/time investment to POINT-002's full-scale re-measurement earlier this session), deliberately not done automatically as part of building C/D.

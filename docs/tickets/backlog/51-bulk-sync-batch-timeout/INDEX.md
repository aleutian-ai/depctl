# Epic: Bulk Sync Batch Timeout

[STRESS-005](../../planned/49-full-loop-stress-testing/STRESS-005-full-cold-sync-real-scale.md) (a full cold sync of real `hashicorp/terraform`, 560+ never-before-synced dependencies) found that `internal/daemon/scheduler.go`'s `maxActionDuration = 30 * time.Minute` wraps **one call to `s.run`**, and for an untargeted `ragctl sync` (no `--dependency`/`--project` filter), `s.run` executes the *entire* pending plan — every action across every registered project — inside that single, fixed budget, not per-dependency. Its own code comment explains the original reasoning honestly: real syncs tested so far "finished in well under a minute even for large repos" — true at every scale tested before now, but never tested against a genuinely large batch of hundreds of never-before-synced real dependencies in one call.

The practical effect: once a few genuinely slow early actions (a real git clone of a large repo, a real embed call) eat into the shared 30-minute ceiling, every action processed after it fails instantly with a generic `context deadline exceeded` — in STRESS-005's run, 358 of 561 attempted dependencies, scattered from the second item processed onward. This reads as hundreds of independent per-dependency failures when the real cause is one shared, exhausted time budget — a diagnosability problem as much as a capacity one.

`internal/daemon/client/client.go`'s `longRunningRequestTimeout = 35 * time.Minute` (the client-side HTTP timeout for the `Sync` call) sits close enough to `maxActionDuration` that STRESS-005's run hit almost exactly 35:00 — both ceilings are effectively the same constraint from two ends of the same request.

**Update — severity reassessed, then reconfirmed real with a second live run.** The specific trigger in STRESS-005's original run (`cloud.google.com/go` alone consuming the entire budget) turned out to be a separate bug, not an inherent property of that dependency: [epic 52 / BOUND-001](../../completed/52-nested-go-module-normalization-boundary/INDEX.md) found `normalizeSources` was normalizing 216 unrelated sibling Go modules bundled in the same repository as if they were part of the dependency being synced. Fixed, and the full untargeted sync was re-run against real `hashicorp/terraform` on a freshly-wiped Qdrant: **154 synced, 407 failed** (up from 1 synced / 560 failed before) — a real improvement, but the run still hit the identical 2100s (35:00) ceiling, this time on a *different* dependency, `github.com/aliyun/alibaba-cloud-sdk-go` — checked directly, a genuine single-module giant (36,132 `.go` files, one `go.mod`, no nested-module boundary to fix), not another instance of BOUND-001's bug. So this epic's underlying question is real, confirmed by two independent large dependencies now, not hypothetical: **any sufficiently large single dependency can still exhaust the shared batch budget on its own**, and every other dependency queued behind it still cascades to instant, misleading `context deadline exceeded` failures. Still worth deciding between the three options below, now with concrete evidence rather than a single data point.

## Tickets
- [BATCH-001](BATCH-001-batch-timeout-options.md) — **done.** Options C (fail the batch cleanly, one aggregate message instead of a cascade) and D (agent-facing scope-planning info — median/p90 observed timing, a confidence-labeled estimate, the real pending-dependency list, surfaced through `sync_progress`) built and tested. Options A/B (raise the ceiling; replace it with a no-progress watchdog) deliberately deferred — A/B change the daemon's liveness/hang-protection contract, a bigger decision than this pass needed to make.

## Non-goals
- Not about any individual operation's own timeout (git clone's `defaultCloneTimeout`, Ollama's per-request `60s` HTTP client timeout) — those are reasonable per-operation bounds already. This epic is specifically about the *aggregate* ceiling applied to an entire multi-dependency batch.

## Status
**Epic stays in `backlog/`** — the real production bug (a wall of misleading `context deadline exceeded` failures once the shared batch budget runs out) is fixed and information-surfaced, but BATCH-001's own re-run-STRESS-005-at-scale acceptance criterion is still open, and A/B remain a real, deliberately undecided question about whether a large batch can ever complete in one invocation.

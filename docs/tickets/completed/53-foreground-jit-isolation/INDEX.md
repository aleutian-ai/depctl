# Epic: Foreground JIT Isolation and Lifecycle Coordination

**All three tickets done — epic closed, 2026-09-28.**

A real, previously-undiscovered reliability gap, found while investigating STRESS-005's batch-timeout finding: `internal/daemon/scheduler.go`'s `s.global sync.Mutex` serializes *every* sync and GC run against *every other* sync and GC run, daemon-wide — not just against runs touching the same project or dependency. Traced precisely: `searchDependencyDocsHandler`'s JIT-sync path (WATCH-019/020) only has a priority-bump mitigation for "another sync already running for *this same* project" (`BumpPriority` returns `false` otherwise, per its own doc comment). If a *different* project's bulk `depctl sync` is holding `s.global` (up to `maxActionDuration` = 30 minutes), a JIT request for an unrelated project's dependency falls through to `Scheduler.Request` → `execute` → `s.global.Lock()` and blocks for the same duration. Every JIT request in the daemon is vulnerable to this whenever any bulk sync is in flight anywhere — this directly undermines depctl's central promise (ask about one dependency, get a fast, correct answer) independent of whether bulk-sync throughput is ever optimized.

This was reached via a longer investigation (STRESS-005 → BOUND-001's nested-module fix → a second confirmed batch-ceiling case against `alibaba-cloud-sdk-go` → a competitive deep-dive against Grounded Docs → a reframe toward "resolve broadly, acquire narrowly" as the intended default UX) and reviewed against detailed external feedback before being scoped. See `docs/tickets/planned/49-full-loop-stress-testing/STRESS-005-full-cold-sync-real-scale.md` and `docs/tickets/completed/51-bulk-sync-batch-timeout/INDEX.md` for that history.

## Design foundation: `sync.RWMutex`, not a bigger rewrite

The existing `s.global` protects two real invariants (per its own doc comment): GC must never delete a generation an active build still needs, and two runs must never race to build the same generation. Neither of those actually requires *unrelated* builds (different projects, different dependencies) to run one at a time — only requires that GC gets exclusive access relative to *every* concurrent build, and that two builds of the *identical* generation serialize against each other specifically.

`sync.RWMutex` gives the first property for free: every build takes `RLock()` (many can hold it at once); GC takes `Lock()` (exclusive, and Go's `RWMutex` blocks new readers once a writer is waiting, so GC can't be starved indefinitely by a continuous stream of new builds — see [COORD-001](COORD-001-lifecycle-coordination-contract.md) for the caveat: this doesn't bound *how long* GC waits if an existing build legitimately holds `RLock` for a long time, only that it isn't overtaken forever). A second, separate keyed primitive (real request coalescing, not just a keyed mutex — see COORD-001) handles the second property: two concurrent requests for the identical generation join one build instead of each starting their own.

## Tickets

- **[COORD-001](COORD-001-lifecycle-coordination-contract.md)** — P0, launch-critical. **Done.** The coordination contract itself: `RWMutex` build/GC gate, keyed request-coalescing for duplicate builds, and an explicit audit of what "one build" must actually cover (every shared-state mutation GC needs excluded from, not just acquisition/embedding).
- **[COORD-002](COORD-002-cross-project-jit-isolation.md)** — P0, launch-critical. **Done.** Proven at both the scheduler level and the real syncVersion/BuildCoordinator integration level — real bbolt/Badger stores, real git fixtures, real `syncVersion`, a deterministic channel-barrier fake embedder standing in for Ollama. The traced cross-project JIT-stranding bug is fixed and directly tested, along with same-dependency coalescing across projects and the queue-wait/phase-timing latency instrumentation the ticket called for.
- **[COORD-003](COORD-003-bulk-worker-pool.md)** — P2, conditional on measurement after COORD-001/002 ship. **Done.** Bounded concurrent worker pool for explicit bulk warm-up (`depctl sync` with no filter), scoped *per sync run* so it can never compete with a JIT request for execution capacity. Default `MaxConcurrency` re-benchmarked on corrected data (2026-09-28, bounded 10-minute-per-level comparison): kept at 2 — real per-dependency latency roughly doubles at concurrency 3/5 versus 2, with no reliable throughput gain to offset it. Its last acceptance box — a live proof against a real daemon that the pool never contends with a concurrent JIT request — closed the same day: a real bulk sync (6 dependencies, pulling in a 32,297-chunk transitive dependency) and a concurrent unrelated JIT sync, both against one real daemon, the JIT one completing in 2.057s while the bulk one was still deep in the huge dependency, no corruption afterward (`doctor` clean, `gc --dry-run` nothing eligible).

## Non-goals (whole epic)
- No general-purpose scheduler, distributed queue, or agent-facing concurrency/priority controls — the MCP-calling agent never chooses queues, workers, or how much to pre-load; that's an operator decision expressed through the CLI (`depctl sync --all`, explicit and deliberate), never surfaced mid-session.
- No attempt to solve per-project registry-source overrides (epic 38, still backlog/unwired) as part of this epic — `generation.Create` is already scoped only by `domain.DependencyVersion`, with no source identity in it at all, a pre-existing gap independent of concurrency. COORD-001's keyed coordination matches that existing identity model exactly rather than expanding it; a future epic picks up per-project source-override correctness if/when epic 38 actually gets wired end-to-end.
- No claim that removing lock contention alone guarantees low JIT latency — if a bulk job saturates Ollama, disk I/O, or CPU, a concurrent JIT request can still be slow for real physical reasons no scheduling change can remove. COORD-002 instruments queue-wait, acquisition, embedding, validation, and publication time separately specifically so this is measurable and distinguishable from lock contention, not asserted away.

# Epic: Pre-v1.0 Operational Hardening

**All four done, 2026-09-28.** Four small, concrete gaps found live during this session's own re-verification work — none discovered by design review or speculation, all hit directly while running real commands against real infrastructure. Bundled into one epic because each is small (a ticket, not an epic-sized effort) and share a theme: things that would quietly surprise or bite an early v1.0 user/operator, distinct from epic 49 (does the system *survive* load/chaos) and epic 53 (JIT isolation correctness).

## Tickets
- [SAFE-001](SAFE-001-scoped-default-collection-name.md) — **done.** `vector.collection` defaulted to the plain, unscoped name `ragctl`, and ambient sync (epic 54/SCOPE-002) fires automatically on first project registration. Two independent instances pointed at the same Qdrant server with default config silently commingled data — hit for real, twice, during this session's own live-verification work (once nearly against real production data). Fixed with both a collision-resistant per-install default collection name and a startup warning if a fresh instance's collection already has foreign data — live-verified end to end in an isolated container.
- [OPS-003](OPS-003-doctor-timeout-under-scale.md) — **done.** `ragctl doctor`'s `checkEmptyActiveGenerations` made one serial, unbounded `VectorBackend.Count` network call per active generation with a non-empty manifest — timed out at real scale (558 generations) against a degraded backend, the exact condition someone runs `doctor` to diagnose. Fixed with a bounded sub-timeout plus a small worker pool. Its real-world payoff: this fix is what let `doctor` complete this exact check against real production data for the first time, surfacing OPS-004's own incident.
- [OPS-004](OPS-004-no-real-way-to-force-rebuild-active-generation.md) — **done.** Found live via the real incident OPS-003's fix surfaced: `ragctl doctor`'s own suggested remedy (`ragctl sync --force`) did not work — `internal/planner`'s `Plan` NOOPs unconditionally whenever a dependency's resolved version hasn't changed, regardless of whether its active generation actually has real backend content, and `--force` has no effect on which actions the planner selects. New `ragctl sync --rebuild --dependency <name>` clears the stale bookkeeping (`Store.ClearActiveGeneration` + `RemoveReference`) before planning, so a genuine rebuild actually happens — live-verified by planting the exact incident shape in a fresh isolated container and confirming the fix.
- [CFG-001](CFG-001-unconsumed-config-surface-audit.md) — **done.** `ServerConfig.HTTPServerConfig` was fully unwired (zero consumers anywhere in the codebase) but shipped in every generated `config.yaml` looking like a real, working option. Removed entirely, matching the project's own "don't ship the abstraction before a second implementation" convention; every other config field audited and confirmed to have a real consumer or be intentionally reserved (`Config.Version`).

## Non-goals (whole epic)
- Not a substitute for epic 49 (full-loop stress/chaos testing) or epic 53 (JIT isolation) — those test correctness/survival under load; this epic is about surprises an operator hits in ordinary, low-load use.
- No new features — every ticket here is either a guard against a known-real failure mode, a fix for a confirmed bug, or a documentation/removal decision on already-shipped surface. Nothing here should grow scope into a redesign.
- REG-008 (epic 38/backlog, the already-implemented-but-CLI-unwired project registry override directory) is a related "built but not reachable" gap, already tracked there — not duplicated into CFG-001.

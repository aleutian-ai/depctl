# Epic: Pre-v1.0 Operational Hardening

**All seven done (2026-09-30).** Closed twice before this: first 2026-09-28 with five done, reopened and reclosed the same day for OPS-005 (STRESS-006's finding), then reopened a second time 2026-09-29 once STRESS-017 surfaced OPS-006. OPS-006 needed a real write-cancellation safety audit rather than a same-day patch — see its own post-implementation note for the full conclusion (no store-corruption risk existed either way; the actual bug was the CLI's own success message, not the wait itself). Small, concrete gaps found live during real re-verification work — none discovered by design review or speculation, all hit directly while running real commands against real infrastructure. Bundled into one epic because each is small (a ticket, not an epic-sized effort) and share a theme: things that would quietly surprise or bite an early v1.0 user/operator, distinct from epic 49 (does the system *survive* load/chaos) and epic 53 (JIT isolation correctness).

## Tickets
- [SAFE-001](SAFE-001-scoped-default-collection-name.md) — **done.** `vector.collection` defaulted to the plain, unscoped name `depctl`, and ambient sync (epic 54/SCOPE-002) fires automatically on first project registration. Two independent instances pointed at the same Qdrant server with default config silently commingled data — hit for real, twice, during this session's own live-verification work (once nearly against real production data). Fixed with both a collision-resistant per-install default collection name and a startup warning if a fresh instance's collection already has foreign data — live-verified end to end in an isolated container.
- [OPS-003](OPS-003-doctor-timeout-under-scale.md) — **done.** `depctl doctor`'s `checkEmptyActiveGenerations` made one serial, unbounded `VectorBackend.Count` network call per active generation with a non-empty manifest — timed out at real scale (558 generations) against a degraded backend, the exact condition someone runs `doctor` to diagnose. Fixed with a bounded sub-timeout plus a small worker pool. Its real-world payoff: this fix is what let `doctor` complete this exact check against real production data for the first time, surfacing OPS-004's own incident.
- [OPS-004](OPS-004-no-real-way-to-force-rebuild-active-generation.md) — **done.** Found live via the real incident OPS-003's fix surfaced: `depctl doctor`'s own suggested remedy (`depctl sync --force`) did not work — `internal/planner`'s `Plan` NOOPs unconditionally whenever a dependency's resolved version hasn't changed, regardless of whether its active generation actually has real backend content, and `--force` has no effect on which actions the planner selects. New `depctl sync --rebuild --dependency <name>` clears the stale bookkeeping (`Store.ClearActiveGeneration` + `RemoveReference`) before planning, so a genuine rebuild actually happens — live-verified by planting the exact incident shape in a fresh isolated container and confirming the fix.
- [CFG-001](CFG-001-unconsumed-config-surface-audit.md) — **done.** `ServerConfig.HTTPServerConfig` was fully unwired (zero consumers anywhere in the codebase) but shipped in every generated `config.yaml` looking like a real, working option. Removed entirely, matching the project's own "don't ship the abstraction before a second implementation" convention; every other config field audited and confirmed to have a real consumer or be intentionally reserved (`Config.Version`).
- [OPS-005](OPS-005-referenced-but-never-built-dependency-invisible-and-unrecoverable.md) — **done.** Found live via epic 49's STRESS-006 (kill-daemon-mid-sync testing, the same day this epic first closed): a kill landing after a dependency's reference commits but before its build reaches `ACTIVE` leaves it permanently un-retriable by any plain `depctl sync` — the exact sibling of OPS-004's case, but invisible to every existing check (`checkEmptyActiveGenerations` has nothing to inspect when there's no active generation at all, and `depctl describe` only reports active generations). New `checkReferencedButNeverBuilt` `doctor` check names the stuck dependency and the `--rebuild` remedy — live-verified by reproducing STRESS-006's exact kill scenario fresh and confirming `doctor` now catches what it previously missed.
- [OPS-006](OPS-006-unbounded-shutdown-wait-blocks-restart.md) — **done.** Found live via epic 49's STRESS-017 (daemon restart during an MCP session, 2026-09-29): `depctl daemon stop` reports `"stopped"` immediately, but the actual process can keep running — still holding the `control.db` lock — for as long as any in-flight sync/GC run takes, with no timeout; confirmed live via a real `kill -QUIT` goroutine dump showing the process genuinely stuck for 3+ minutes. The write-cancellation audit deferred at the time (2026-09-29) concluded (2026-09-30) there was never a store-corruption risk: `runDaemonRun` never closes a store until `Server.Serve` returns from `Scheduler.Wait()`, and a `sync.WaitGroup` can't return while a tracked goroutine is still running, so `Close()` can never race an in-flight write regardless of how long the wait takes. The real bug was narrower than the ticket assumed: `depctl daemon stop` was watching the wrong signal (the socket, which closes well before the process actually exits) — fixed by checking the real PID's liveness instead, live-verified against a real separate daemon process.
- [OPS-007](OPS-007-git-mirror-lock-rebuilt-per-sync-call.md) — **done.** Found live via epic 49's STRESS-007 (concurrent cross-project sync, 2026-09-29): two real, concurrent syncs needing the same underlying git repository at different tags raced on its shared mirror directory — `EnsureMirror`'s own in-process `mirrorLocks` lock existed specifically to prevent this, but `RunSync` built a fresh `git.Cache` (with a fresh, empty lock map) on every call, so the lock never actually protected two calls from each other. Reachable only once epic 53 removed cross-project sync serialization. Fixed by hoisting `git.Cache` construction to once per daemon lifetime (`engine.gitCache`, built in `newEngine`, matching the existing `syncSem` pattern) instead of once per `RunSync` call.

## Non-goals (whole epic)
- Not a substitute for epic 49 (full-loop stress/chaos testing) or epic 53 (JIT isolation) — those test correctness/survival under load; this epic is about surprises an operator hits in ordinary, low-load use.
- No new features — every ticket here is either a guard against a known-real failure mode, a fix for a confirmed bug, or a documentation/removal decision on already-shipped surface. Nothing here should grow scope into a redesign.
- REG-008 (epic 38/backlog, the already-implemented-but-CLI-unwired project registry override directory) is a related "built but not reachable" gap, already tracked there — not duplicated into CFG-001.

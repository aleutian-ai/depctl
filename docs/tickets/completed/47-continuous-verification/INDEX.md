# Epic: Continuous Verification

A 2026-09 design review found a recurring pattern worth closing structurally rather than relying on catching again by luck: this session found two real bugs (WATCH-019/020's daemon-HTTP sentinel-identity loss, GRAPH-003's module-vs-package-path bug) that every unit test passed against, and that only a human deliberately running a real, live end-to-end session ever caught — plus several stale documentation claims (tool counts, "disabled by default" language, missing acquisition-behavior changes) that only got fixed because someone happened to reread the docs closely. Both are the same failure mode: **the thing that would have caught it exists only as a manual, one-off action someone has to remember to do, not as something CI enforces every time.**

This epic closes that gap for the two clearest instances of it, without inventing a general "make everything foolproof" program:
- [VERIFY-001](VERIFY-001-ci-live-mcp-smoke-test.md) — **done.** A real `depctl serve` subprocess, spawned over stdio, driven by a real MCP client, running in CI on every push — the exact shape of test that would have caught both live-testing-only bugs this session found, made to run automatically instead of manually. Passed on its first real run.
- [VERIFY-002](VERIFY-002-docs-tool-surface-drift-check.md) — **done.** A small, mechanical CI check that the MCP tool list claimed in `docs/internal/mcp.md`/`docs/features/query-serving.md` actually matches what `internal/mcp/tools.go` registers. Its first real run immediately found two genuine, pre-existing doc bugs (both missing `scan_project` entirely, both with a wrong tool count) that this session's own earlier documentation sweep had missed — proving the ticket's value on contact. `README.md` was dropped from scope after running it, since that doc is deliberately non-exhaustive by design — see the ticket's own post-implementation note.

## Non-goals
- No general documentation-freshness/semantic-drift detector — that's an open-ended, low-precision problem (see VERIFY-002's own non-goals for why it stays narrow and mechanical instead).
- No requirement that every future integration point gets its own CI smoke test — VERIFY-001 covers the MCP-over-stdio path specifically, since that's the one real agents actually use and the one that's bitten twice; a different future integration boundary breaking silently is a new, separate problem to solve when (if) it happens, not preemptively solved here.
- No change to the existing in-process test suite (`sdkmcp.NewInMemoryTransports()`-based tests in `internal/mcp`) — those stay exactly as they are, testing MCP protocol/handler logic quickly; VERIFY-001 adds the one thing they structurally can't cover (the real subprocess/stdio/wire boundary), it doesn't replace them.

# ragctl — Completed Tickets

Epics whose every ticket is fully shipped: `**Status:** done` in every ticket file, every Acceptance Criteria box checked, and cross-verified against `docs/architecture.md` (which remains the authoritative "what's actually implemented" narrative — this directory just mirrors that verdict at the ticket-tracking level). See [../planned/README.md](../planned/README.md) for the v0.1 critical-path epics still in progress, and [../backlog/README.md](../backlog/README.md) for deferred scope.

An epic moves here only when **every** ticket inside it is done — a mixed epic (some tickets shipped, some genuinely gapped) stays in `planned/` until that's no longer true. Closing a ticket here doesn't always mean the original sketch got built literally: `CORE-001` and `STORE-001` (below) closed by *reconciling* the ticket to a better shape later epics actually proved out, not by building two now-superseded types just to make an old checklist green. See their own Post-implementation notes for the reasoning — that distinction ("ticket incomplete" vs. "spec drift from real implementation experience") is worth preserving, not collapsing into a flat done/not-done state.

57. [57-js-python-structured-api-normalizers](57-js-python-structured-api-normalizers/INDEX.md) — `NORM-008`/`NORM-009`: per-symbol, signature-level structured API documentation for JS/TS (`.d.ts` + a JSDoc-only fallback for packages with no `.d.ts` at all) and Python (static `ast`-based extraction, never importing/executing the target package) — the `godoc` equivalent for both ecosystems. The JSDoc fallback's original "two-phase acquisition" blocker turned out to already be solved by plumbing epic 56 built for a different reason. 59. [59-python-package-subdir-discovery](59-python-package-subdir-discovery/INDEX.md) — `SUBDIR-001`: real `pydantic` — one of the most widely used PyPI packages — was silently producing zero structured docs because its `__init__.py` lives in a same-named subdirectory of its repo root, a layout Python acquisition couldn't discover (epic 56's own disclosed non-goal, more common than a monorepo edge case). Built in two passes: discovery itself worked on the first try, but live-verifying past the fixture tests found scoping *every* sparse pattern (including README/LICENSE) to the discovered subdirectory broke acquisition outright for packages whose real docs live at the true repo root, not duplicated inside the source subdirectory — fixed by keeping doc patterns unscoped. `pydantic` itself still shows no structured docs, but for an unrelated, already-disclosed reason (its `__getattr__`-based lazy re-exports defeat static extraction) — this epic's own job (never silently lose content) is done and confirmed.
60. [60-structural-preservation](60-structural-preservation/INDEX.md) — `STRUCT-001..004`: stop discarding cheap structure the normalizers/chunkers already derive in-memory. `STRUCT-001` adds a structured `section_path` alongside the Markdown chunker's flat `heading_path`. `STRUCT-002` replaces the Markdown normalizer's document-wide `code_languages` set with structured per-block fenced-code records (index, language, content, section path). `STRUCT-003` promotes `dependency`/`version`/`source_type` onto every `domain.Chunk.Metadata` (both chunkers), so a caller holding only a `Chunk` never needs a second Badger lookup of its parent object. `STRUCT-004` computes a human-readable breadcrumb string (`grpc-go@1.72.0 > Authentication > Transport Credentials`) from STRUCT-003's promoted fields and surfaces it on `query.ResultChunk` and the `search_dependency_docs` MCP tool's output. Renumbered from 21 (2026-09) — collided with the pre-existing, unrelated `completed/21-node-resolver`. Shipped straight through in one pass; all four tickets' own current-source assumptions matched the tickets' sketched shapes verbatim, so no design deviations were needed.
51. [51-bulk-sync-batch-timeout](51-bulk-sync-batch-timeout/INDEX.md) — `BATCH-001`: an untargeted `ragctl sync` against a large real project couldn't complete in one invocation — `internal/daemon/scheduler.go`'s `maxActionDuration` wrapped the *entire* pending plan in one 30-minute ceiling, not per-dependency, so once exhausted every remaining action cascaded into a misleading, indistinguishable wall of `context deadline exceeded` failures. Found live by STRESS-005 against real `hashicorp/terraform`. Option C (fail the batch cleanly, one aggregate message) and Option D (agent-facing scope-planning info — median/p90 observed timing, a confidence-labeled estimate, the real pending-dependency list, all surfaced through `sync_progress`) shipped; Options A/B (raise the ceiling; a no-progress watchdog) deliberately deferred, since epic 53/COORD-003 separately removed the aggregate ceiling from the sync path entirely. Real-scale re-run (2026-09-26) against real `hashicorp/terraform` (569 dependencies, 11 Go projects once submodules are counted): 555 synced, 14 failed (unrelated causes), zero "budget exceeded" occurrences across the ~1h52m run — the underlying capacity fix held at scale, and C's clean-stop path was never even needed. That same real-scale session also found and fixed a related, separate `sync_progress` bug live (see epic 51's own `BATCH-001` post-implementation note): `Total`/`Done`/`Failed` all being zero was indistinguishable between "never synced" and "synced, found nothing new to build," which misled a real MCP session into concluding the sync tool was disabled — fixed with a new `Ran` field threaded through `api.SyncProgress`/`SyncProgressOut`.
43. [43-local-cache-reuse](43-local-cache-reuse/INDEX.md) — `GIT-004..007`: `internal/source/git.Cache` always did a full, second `git clone --mirror` for every dependency regardless of what a user's own package manager (or a personal offline corpus) already had locally. GIT-005 (blobless clone + sparse checkout) shipped earliest. GIT-004 adds a local-cache fast path: Go/Python via each ecosystem's own machine-global cache (`go env GOMODCACHE`; the active `python3`'s `site-packages`, matched via `dist-info`'s own `top_level.txt`, never a name-based guess), Node via the *specific project whose sync action triggered the build*'s own `node_modules` (threaded through as a new `projectRoot` parameter, since `domain.Generation` itself deliberately carries no project reference) — measured, a real dependency already in `$GOMODCACHE`: 23.5x speedup. GIT-006 adds an optional external-directory search laid out in ragctl's own exact mirror convention (a backup of another machine's cache); GIT-007, split out as its own ticket rather than expanding GIT-006's scope, adds a second search tier for an arbitrary directory of real git working-tree checkouts (e.g. a personal `~/offline-knowledge` corpus), matched by each checkout's own `origin` remote instead of path convention. GIT-007's own required real-world measurement caught a real bug every synthetic test had masked: `splitGitURL` never normalized a trailing `.git` suffix, so two equally common forms of the same repository URL didn't compare equal — fixed at the root (moved into `splitGitURL` itself, not patched at the one call site that happened to find it) rather than patched narrowly. Measured after the fix: 2.5x speedup against a real `~/offline-knowledge` checkout.

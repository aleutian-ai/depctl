# ragctl — Planned Tickets (v0.1 critical path, in progress)

Source: `ragctl_implementation_plan.md` + `ragctl_design_spec.md`. See also [../completed/README.md](../completed/README.md) for fully-shipped epics and [../backlog/README.md](../backlog/README.md) for deferred epics (additional ecosystems, additional vector backends, eval/observability/security, optional integrations).

Each numbered directory is an epic. Each epic has an `INDEX.md` with the epic's goal and a linked list of its tickets. Every ticket is a self-contained spec (goal, non-goals, simplicity constraints, design, tests, acceptance criteria) — implementable without re-reading the source docs. A ticket's `**Status:**` line is `planned` until every one of its Acceptance Criteria boxes is genuinely checked, at which point it becomes `done` — see `docs/architecture.md` for the authoritative narrative of what's actually shipped.

**Guiding rule across all tickets:** keep implementations as simple as possible. Build one reference implementation per interface before adding more (one resolver, one vector backend, one embedder). Do not build the interface abstraction until a second implementation is imminent.

Epic 61 shipped once too but has since reopened a second time (see below); the two below are the only ones still genuinely open.

49. [49-full-loop-stress-testing](49-full-loop-stress-testing/INDEX.md) — STRESS-001 through STRESS-018: real-scale, real-concurrency, and adversarial (`kill -9`) testing of `scan → sync → gc → serve`, all against real infrastructure (real daemon, real Qdrant, real Ollama, real public dependencies) rather than fixtures or fakes — everything shipped through epic 48 was proven *correct*; this epic proves it *survives*. 13 of 18 tickets done: STRESS-001..005 re-verified live with no regressions (2026-09-27); STRESS-006 (kill daemon mid-sync, 2026-09-28) found a real gap (a kill landing between a dependency's reference commit and its build reaching `ACTIVE` leaves it permanently un-retriable and invisible to every existing check) — filed and fixed same-day as epic 61's `OPS-005`; STRESS-010 (repeated real failure injection, 2026-09-29) confirmed that same recovery pattern generalizes to clean failures too (bad ref, embedder down, vector backend down all left the exact same un-retriable-without-`--rebuild` state), not just kill-interruptions; STRESS-012 (orphan GC after real failures) covered live in the same STRESS-010 session — a real `gc --orphans` run correctly deleted all three real casualties while leaving each dependency's own healthy, active generation untouched; STRESS-011 (reference-based GC at scale, 2026-09-29) deleted 37 real grace-expired candidates cleanly, confirming `PlanGC`'s active-generation-skip is genuine, deliberate design (a dropped reference alone is never GC-eligible while its version is still `active`) rather than a gap; STRESS-014 (repeated GC cycle idempotency, 2026-09-29), run against real production, found and cleanly cleared 9+9 real previously-uncollected candidates on its first pass, then confirmed 2 further repeats of each command correctly short-circuit to fast, clean no-ops; STRESS-013 (GC and a queued sync under real daemon load, 2026-09-29), updated for epic 53's `BuildCoordinator` (`gate sync.RWMutex`, replacing the single global mutex this ticket originally described), confirmed full real GC/sync exclusion in both request orderings with two genuinely separate client processes — one side always blocks the entire duration of the other's real work, in both directions, with no interleaving corruption; STRESS-016 (`explain_call_site` at scale, 2026-09-29), run against ragctl's own already-synced real repo, correctly resolved all 15 real call sites (5 external deps, 2 interface dispatches, 1 stdlib, rest internal) and found one real latency outlier worth a future perf pass (a large struct-literal call site at 3.00s vs. 380-965ms for everything else); STRESS-017 (daemon restart during an MCP session, 2026-09-29) confirmed the restart/reconnect story is solid (a live session's next call self-heals once any daemon rebinds the socket, no reconnect logic needed; a graceful stop or `kill -9` always produces a clear error, never a hang), but found a real, more serious gap along the way — `Scheduler.Wait()`'s unbounded shutdown-time wait can leave a "stopped" daemon's process (and its control.db lock) alive for as long as any in-flight sync takes, confirmed live via a real 3-minute stuck process's goroutine dump — filed as epic 61's `OPS-006` rather than fixed same-day, since a safe fix needs a store-write-cancellation audit first. Remaining crash/chaos/GC-at-scale-under-load/concurrent-MCP-session coverage is unwritten — the least-tested real risk area in the project.
